# Setup (v0.4.3)

This guide reproduces the reference setup: Windows, Paper 1.18.2, TerraPlusMinus, and the Clark County, Nevada data. Steps marked **⚠ hard-coded** need a source edit until the portability work lands ([ROADMAP.md](ROADMAP.md)).

Use a **test server or a copy of your world** first. The tool has a full undo, but test on a copy anyway.

## 1. Requirements
| piece | version | notes |
|---|---|---|
| Java JDK | 17 | Full JDK, not a JRE: the prep step compiles `GeoServer.java` with `javac`. |
| Paper | 1.18.2 | With **TerraPlusMinus** installed and generating your world. |
| TerraPlusMinus JAR | 1.3.3 | A copy on disk is also used by the prep worker for projection and terrain. |
| Python | 3.11+ | In a virtualenv. |
| Disk | ~10 GB | LiDAR cache (capped at 8 GB), OSM index, chunk plans. |
| Internet | — | For LiDAR tiles, and Overpass outside the local index. Nothing is uploaded. |

## 2. Folder layout
The current code expects this layout. You can use another root if you change the **⚠ hard-coded** paths listed in step 5.


## 4. Build the local OSM index
The index is optional, but it is much faster: about 10 s per new chunk, against 1–2 minutes through Overpass.
1. Download your region's `.osm.pbf` from [Geofabrik](https://download.geofabrik.de/). Nevada was used here.
2. Write a small provenance JSON next to it: source URL, download date and SHA-256.
3. Build the index:
   ```bat
   C:\BTE-Migration\venv\Scripts\python prep\osm_index_build.py nevada-latest.osm.pbf nevada-latest.provenance.json C:\BTE-Migration\shelltool\osm-extract\clark_osm_index.sqlite -116.10,35.00,-114.00,36.90
   ```
   The last argument is the coverage box (west, south, east, north in lon/lat). Inside the box, a missing feature means "not mapped in OSM". Outside it, the tool falls back to Overpass.

## 5. Paths and region settings (⚠ still hard-coded in v0.4.3)
| file | line / setting | what it is |
|---|---|---|
| `prep/shelltool_prep.py` | `INDEX = ...` | Path to the OSM index |
| `prep/shelltool_prep.py` | `P = json.load(open(...polygons.json))` | Protected-zone polygon (`strip_mc`, in block coordinates; buffered by 500 blocks) |
| `prep/shelltool_prep.py` | `open(...shells.txt)` | Plugin data file |
| `prep/shelltool_prep.py` | LiDAR dataset names (near the `EPT` constant) | USGS 3DEP datasets for Clark County. Pick the ones covering your area from the [USGS EPT bucket](https://usgs.entwine.io/). |
| `prep/geo.py` | `JAVA`, `JAR`, `TPP_CACHE` | JDK, TerraPlusMinus JAR, and the terrain tile cache |

**Outside the US** there is no 3DEP LiDAR. Buildings then get only an orange ground outline, and roads work normally.

## 6. Plugin data file (`shells.txt`)
The plugin refuses to start without a protected-zone polygon (`POLY strip ...`). The Las Vegas file is generated by `prep/shelltool_export.py` from the Summerlin pilot plan, which isn't in this repo.

For another region, write a minimal file by hand. Coordinates are Minecraft block X Z pairs:
```
# SummerlinShellTool data v1
POLY strip <x1> <z1> <x2> <z2> <x3> <z3> ...
```
- If you have nothing to protect, give `strip` a tiny polygon far from your build area.
- Make it match `strip_mc` in your `polygons.json`, because the plugin and the prep worker check it independently.

## 7. Get the plugin
**Easiest:** download `SummerlinShellTool-0.4.3.jar` from the [v0.4.3 release](https://github.com/RyanPendergast12/Moria-BuildTheEarthTool/releases/tag/v0.4.3).

**Or build it.** No Gradle or Maven yet. Compile against the JARs in your Paper server's `libraries` folder, after the server has been started once. In PowerShell:
```powershell
cd plugin
$cp = (Get-ChildItem <server>\libraries -Recurse -Filter *.jar).FullName -join ';'
javac --release 17 -nowarn -cp $cp -d build\classes src\main\java\org\bte\summerlin\shelltool\ShellToolPlugin.java
copy src\main\resources\*.yml build\classes\
jar cf SummerlinShellTool-0.4.3.jar -C build\classes .
```

## 8. Install and configure
1. Stop the server with `stop`. Don't close the window.
2. Copy `SummerlinShellTool-0.4.3.jar` into `<server>\plugins\`, and remove any older `SummerlinShellTool-*.jar`.
3. Start the server once. This creates `plugins\SummerlinShellTool\config.yml`. Then stop it again.
4. Edit `config.yml`:
   - `required-server-port`: your server's port. The plugin disables itself on any other port, which stops it running on the wrong server by accident.
   - `world`: the only world it may write to.
   - `allowed-players`: builder UUIDs. Look them up at namemc.com.
   - `prep-python`, `prep-script`, `cache-dir`: absolute paths from step 2. The prep scripts must be the ones from the **same release** as the JAR: the plugin re-prepares any chunk planned by another preparation pipeline.
   - Overpasses (optional, all off by default):
     - `overpass-enabled: true` turns them on.
     - `overpass-mode`: `auto` (every eligible crossing; default) or `allowlist` (only `overpass-crossings`).
     - `overpass-exclude` blocks single crossings; `overpass-min-clearance` sets the air blocks required (default 4).
     - `overpass-crossings` lists the allowed crossing keys (allowlist mode).
     - `overpass-piers` stays `false` (inferred piers).
     - `overpass-approach-grade` sets raised approaches: 0 = off, 0.04–0.10 allowed, tested at 0.06.
5. Copy `shells.txt` to `plugins\SummerlinShellTool\`.
6. Start the server. The log should show `Enabling SummerlinShellTool v0.4.3`, with no error after it.

## 9. First use
```
/shelltool content both   ← shells + roads (+ enabled overpasses); the reply confirms mode and content
/shelltool preview        ← throw a snowball at the ground: reports only, places nothing
/shelltool on             ← throw again to build
/shelltool undo           ← shows what undo would restore
```

## Singleplayer (one builder)
Run the Paper server on your own PC (`online-mode=true`, no port forwarding) and connect to `localhost`. That's the whole "singleplayer" setup.

## Saving and stopping
- Always stop with `stop`. It saves every world.
- Closing the window or killing Java loses up to 5 minutes of building, since the last autosave.
- The tool's undo ledger is written after every batch, so undo data survives either way.
